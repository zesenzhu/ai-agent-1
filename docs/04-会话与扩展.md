# 04 会话与扩展

## 会话文件

默认写到 `.agent-session.json`，可用 `AGENT_SESSION_FILE` 或 `--session` 改路径。

```json
{
  "version": 1,
  "updatedAt": "2026-11-02T16:01:22.425Z",
  "messages": [
    { "role": "system", "content": "…" },
    { "role": "user", "content": "帮我算 (12+3)*4" },
    { "role": "assistant", "content": null, "tool_calls": [{ "id": "call_1", "…": "…" }] },
    { "role": "tool", "tool_call_id": "call_1", "name": "calculate", "content": "(12+3)*4 = 60" },
    { "role": "assistant", "content": "结果是 60。" }
  ]
}
```

设计要点：

- **整份消息数组落盘**。恢复会话时 `agent.loadHistory()` 会把 system 消息换成当前提示词——提示词改了，旧会话立刻生效，不会残留旧契约。
- **原子写入**：先写 `.tmp` 再 `rename`。进程被杀不会留下半截 JSON。
- **容错读取**：文件损坏或版本不匹配时返回空数组，不让历史拖垮启动。
- **`version` 字段**：以后改结构可以按版本迁移，而不是猜。

`/reset` 会同时清空内存与文件。

## 历史裁剪

`AGENT_MAX_HISTORY` 控制保留多少条非 system 消息。超出时从最早的开始丢。

唯一的坑：**不能把历史裁到 `tool` 消息开头**。`tool` 消息必须紧跟它对应的 `assistant(tool_calls)`，否则接口报 400。所以裁剪时会向前跳过连续的 `tool` 消息：

```ts
let start = rest.length - maxHistory;
while (start < rest.length && rest[start]?.role === 'tool') start += 1;
```

更完整的做法（本示例未实现）：

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 条数裁剪（当前） | 简单、可预测 | 早期信息直接丢失 |
| 摘要压缩 | 保留语义 | 多一次模型调用，可能失真 |
| 向量检索 | 长期记忆 | 需要 embedding 与索引 |
| 结构化记忆 | 精确（用户偏好、常用账户） | 需要设计抽取与写入时机 |

对记账类场景，**结构化记忆**通常比全文检索更值：用户说「记到招行卡」，你需要的是账户 ID 的稳定映射，不是语义相似的旧对话。

## 事件流：换 UI 只换一层

Agent 对外只暴露事件流（`src/agent/agent.ts` 的 `AgentEvent`）：

| 事件 | 何时 | 携带 |
| --- | --- | --- |
| `delta` | 模型每吐一段文本 | `text` |
| `tool_call` | 即将执行工具 | `id` / `name` / `args` |
| `tool_result` | 工具执行完毕 | `id` / `name` / `ok` / `content` |
| `final` | 本轮结束 | `text` |
| `step_limit` | 触达步数上限 | `steps` |

终端渲染在 `src/cli/repl.ts`。换成 Web / 飞书 / 微信只需要替换这一层：

```ts
for await (const event of agent.run(input, { workspace })) {
  if (event.type === 'delta') res.write(event.text);
  if (event.type === 'tool_call') socket.emit('tool_call', event);
  if (event.type === 'final') socket.emit('done', event.text);
}
```

注意 `delta` 与 `final` 的分工：流式时内容已经在 `delta` 里发过了，`final` 只用于结束信号，否则前端会显示两遍。

## 往下能加什么

按「投入产出比」排序：

**1. 并行工具调用**
现在 `for` 循环是串行的。模型一次返回多个 `tool_calls` 时，彼此无依赖就应该 `Promise.all`。注意结果顺序：`tool` 消息顺序不重要，但 `tool_call_id` 必须一一对应。有副作用的工具（写文件、下单）不要并行。

**2. 写操作人工确认**
把 `Tool` 扩展成带 `requiresApproval: true`，执行前发一个 `approval_required` 事件，等 UI 回传批准。记账的「新增/删除账单」必须走这条。

**3. 重试与降级**
网络错误、429 限流、5xx 应该指数退避重试；工具错误不需要重试（模型会自己改）。`LLMError` 已经带了 `status`，可以直接据此分流。

**4. 可观测性**
每个请求加 `traceId`，记录：步数、工具名与耗时、prompt/completion token、失败原因。`ChatResult.usage` 已经有 token 数（流式下需要服务端支持 `include_usage`）。没有这些数据，成本和故障都无从分析。

**5. MCP**
把工具层换成 MCP 客户端，就能直接复用社区生态里的工具服务器。接口上只是 `ToolRegistry` 的数据来源变了，agent 循环不用改。

**6. 多 agent**
把「规划」和「执行」拆成两个 agent，或者按领域拆（记账 agent / 统计 agent）。代价是上下文传递和错误传播变复杂，先用单 agent 把工具打磨好。

**7. 结构化输出**
需要稳定的机器可读结果时（例如「解析这句话生成账单草稿」），让模型输出符合 JSON Schema 的对象，而不是解析自然语言。OpenAI 的 `response_format: json_schema` 是标准做法。

## 接进 xb-jizhang 的路径

主项目是 NestJS + Next.js，agent 合理的形态是**后端的一个模块**，而不是独立进程：

```text
Next.js 页面
   │ POST /api/agent/chat  (SSE)
   ▼
NestJS AgentModule
   ├── AgentService   → 复用本示例的 Agent 类
   ├── ToolsService   → 工具内部调用现有 Service（账单、分类、统计）
   └── SessionStore   → 换成 PostgreSQL / Redis，按 userId + ledgerId 分片
```

必须遵守主项目的约束（`.agent/AGENTS.md`）：

- 工具执行要带上**当前用户**的身份，走现有 Guard 与账本成员校验，不能用服务账号绕过；
- 金额一律整数分；
- 新增账单带客户端幂等 ID，修改带版本号；
- 会话存储按用户隔离，不能出现跨用户读到历史；
- 任何写操作工具都要有人工确认与审计记录。

一个具体的工具设计参考见 `03-编写工具.md` 末尾的 `create_transaction`。
